## Context

Every element is drawn in one global look (ADR 0005): ink outlines, the theme's
primary colour as the shape fill, yellow paper for notes. People want to tell
shapes apart by colour and to mark some lines as dashed or heavier, the way
Excalidraw-style boards allow. The human lifted the SPEC §2 styling exclusion
on 2026-10-30 (addendum D10), for colours, stroke widths and stroke styles
only.

The forces are the same ones ADR 0004 and ADR 0005 dealt with:

- A style value is stored, validated by Ash and PostgreSQL, sent in events,
  rendered by two renderers forced equal by a parity fixture, and offered by a
  toolbar. If each of those places kept its own list of colours they would
  drift, the way the kind lists did before ADR 0004.
- Not every property makes sense for every kind: a line has no fill, text has
  no stroke width. The rule has to hold in the database, not only in the UI.
- Colours have to work in the light and the dark theme. A stored hex value
  would be right in one theme and unreadable in the other.
- Styles are edited concurrently with moves and resizes. ADR 0001 makes each
  element one server-ordered last-write-wins register; a style edit must not
  undo a concurrent resize, or the other way round.
- The migration and the release deploy independently: an old server must keep
  writing valid rows after the migration, and existing elements must look the
  same as before.

## Decision

1. **One registry of tokens.** `Sketch.Canvas.Style` declares four properties
   and their tokens, in panel order, with the first token as the default:
   - `stroke_color`: `ink`, `red`, `green`, `blue`, `orange`;
   - `fill_color`: `auto`, `none`, `red`, `green`, `blue`, `yellow`;
   - `stroke_width`: `thin`, `bold`, `extra_bold`, each with a nominal width
     of 2, 4 and 6 px;
   - `stroke_style`: `solid`, `dashed`, `dotted`.

   A token is a name, never a colour value. `auto` is the kind's own fill
   (the theme's primary colour for shapes, paper yellow for notes), so every
   existing element and every row an old server inserts keeps today's look.
   The registry also holds each width's sketch width (three quarters of the
   nominal width, since a hand-drawn outline is two passes, ADR 0005) and the
   dash pattern of every non-solid style at every width.
2. **Four attributes on `Element`.** `stroke_color`, `fill_color`,
   `stroke_width` and `stroke_style` are `Ash.Type.Enum` types whose values
   come from the registry, not null, defaulting to the first token. PostgreSQL
   CHECKs (`<property>_known`) list the tokens, and the migration adds the four
   columns with those defaults and the CHECKs only (expand only), generated by
   `mix ash.codegen`.
3. **Kinds declare what applies.** `Sketch.Canvas.Kind` gains `style`, the
   list of properties that apply to the kind: every property for rectangles,
   diamonds and ellipses; stroke colour, width and style for lines, arrows and
   freehand strokes; fill and stroke colour for notes; stroke colour for text.
   Stroke colour is the colour of the kind's ink: the outline of shapes and
   lines, the glyphs of text and notes. A note's outline belongs to its paper
   and follows its fill. `Sketch.Canvas.Kinds` fails to compile if a spec
   names a property the registry does not have. An inapplicable property must
   hold its default: an Ash validation per property (atomic, so it also checks
   the stored kind in `commit_style`) and a PostgreSQL CHECK per property
   (`<property>_fits_kind`), both derived from the specs.
4. **`commit_style`.** A third update action accepts only the four style
   attributes and applies `atomic_update(:version, expr(version + 1))`, like
   `commit_position` and `commit_shape`, and publishes the same element event
   on the board topic. The code interface is `commit_style` with
   `get_by: [:id, :board_id]` (A07). `create` accepts the style too.
5. **Style lives in the element's register.** There is still one version per
   element. Each update action sets only its own columns
   (`commit_position` the position, `commit_shape` the box, points and text,
   `commit_style` the style), in one atomic `UPDATE … RETURNING`. Row locking
   serialises concurrent commits, every commit increments the version, and
   the event a commit publishes is the whole row after it. So a style commit
   and a shape commit that race both land, in some order, and the event with
   the highest version holds both: no lost update, and the client merge rule
   (keep the highest version) is unchanged. The commit-model property and the
   concurrent-commit test include style commits.
6. **Rendering from tokens.** Renderers on both sides map tokens to classes and
   attributes, never to colours: `stroke-palette-<token>` on strokes,
   `fill-palette-<token>` on fills, `ink-palette-<token>` on glyphs,
   `note-edge-<fill token>` on a note's outline, `stroke-width` from the width
   and `stroke-dasharray` for a dashed or dotted style. An arrow's head uses
   the marker for its stroke colour (`#arrowhead-<token>`). The colours are
   CSS variables in `assets/css/app.css` with a light and a dark value each.
   `mix sketch.gen.manifest` copies the registry and each kind's `style` into
   the client manifest, and the render parity fixture renders a sample of
   style combinations for every kind.
7. **Panel and next-element style.** A properties panel, rendered from the
   registry by `SketchWeb.StylePanel`, shows the properties that apply to the
   selected element or, with no selection, to the active drawing tool's kind,
   as swatches and segmented buttons with `aria-pressed`. The canvas hook owns
   it, like the tool selection: with an element selected a change pushes
   `commit_style`, and every change also becomes the next element's style,
   local UI state applied, filtered to the drawn kind's properties, to the
   draw preview and to `create_element`. `BoardLive` checks every style param
   against the registry with guards and drops the event otherwise.

## Alternatives considered

- **Hex colours or a free colour picker**: the most flexible, but a stored hex
  value cannot follow the theme, and the database could only check its syntax.
  Rejected; tokens keep the stored data small, checkable and themeable.
- **One JSON `style` map or an embedded resource**: one column instead of four
  and easy to extend, but CHECKs on JSON are clumsier, partial updates of a
  map need care to avoid overwriting a concurrent change, and the generated
  enum types would be lost. Rejected.
- **Per-kind defaults instead of `auto`**: a note could default to `yellow` and
  a rectangle to an `orange`, but a column default is the same for every row,
  so old servers and existing rows would need per-kind backfills, and the
  rectangle fill would stop following the theme's primary colour. Rejected.
- **A separate version (register) per property group**: style commits would
  never even contend with moves, but the client merge, the previews' base
  version (addendum D2) and the tombstone rule all assume one version per
  element. Not needed, since each action writes only its own columns.
  Rejected.
- **`context-stroke` for the arrowhead**: one marker for every colour, but
  browser support for SVG 2 context paint is recent and uneven. Rejected in
  favour of one small marker per stroke colour, generated from the registry.
- **`Ash.Type.Union` per kind (ADR 0004)**: kinds still share one box and the
  same four style columns; applicability is a list per kind. Still not needed.

## Consequences

A colour, width or style is added in one place, the registry, plus its CSS
variables in both themes; the manifest, the Ash types, the validations and the
CHECKs follow, and `ash.codegen --check`, `sketch.gen.manifest --check` and
the parity fixture fail until they are regenerated. Adding a kind now also
means choosing its style properties. Removing a token, or changing a default,
is a contract change for stored rows and needs an expand/contract migration.

The stored tokens lock in names, not colours, so the palette can be retuned
for either theme without a migration. `auto` is a token whose colour depends
on the kind; that is the price of keeping every existing drawing unchanged.

Style edits are not previewed to other browsers before they commit, and a
style commit carries no base version: two people restyling the same element
at once both commit, and the later one wins, as for moves. Revisit if
opacity, roughness (which would join the seed, ADR 0005), fonts or per-point
styles are approved, or if a property needs its own register.
